# Snapzy performance baseline: decision 54 research

Date: 2026-09-23. Author: Codex research agent; official-source web findings supplied by the coordinating Codex agent. No Cursor model was used.

**Recommendation: C — use macOS Screenshot as the only v1 baseline.** This is an explicit reduction of decision 22's original comparator scope, not evidence that its signed-Snapzy requirement has been fulfilled. It preserves a usable comparator without substituting an unvalidated binary or waiting on an unverified compiler fix. It is consistent with decision 54's **provisional** Snapzy direction; this report does not ratify that direction or amend decisions or tickets. The 500 ms placeholder remains a placeholder until macOS measurements exist. [1]

## Scope and observed failure

This investigation was read-only except for this report. No git commands, builds, launches, clone edits, signing changes, or paid APIs were used. The inspected build helper is the supplied `Tools/Performance/build-snapzy.sh` in the main workspace; no branch identity was checked with git.

Decision 22 requires measuring both the built-in macOS screenshot tool and a **signed Snapzy release before setting targets**. Decision 54 delegates route selection and currently records macOS-only comparison under a heading explicitly saying the immediate forks are provisional until vetting reports arrive. Therefore none of A–C literally completes the original two-comparator requirement. C is a recommended scope change, not semantic compliance with the old wording. [1]

The helper pins Snapzy revision `837fc73d9b55dfde203e9d14aeb8c8fae4f0add7`, archives the reference into scratch, resolves locked dependencies, and invokes Release for the host architecture. It explicitly disables signing and says unsigned results are not decision 22's baseline. Fixing compilation alone would consequently leave a separate signing/launch-verification gap. [2]

The existing log records the x86_64 Release invocation, `-O` and whole-module optimization, Apple Swift **6.3.2**, and effective Swift language version **5.10**. The compiler fails during `EarlyPerfInliner` on `ThreadSafeDictionary.deinit` at `S3MultipartUploader.swift:322:21`; the build ends `BUILD FAILED`. The helper class at that line has no explicit `deinit`, so the crash concerns its compiler-generated destructor, not an authored destructor on `S3MultipartUploader` itself. This demonstrates a compiler crash in that optimization pipeline; it does not establish its root cause or prove any workaround builds successfully. Xcode 26.5 is the brief's environment identification; the log also shows use of the macOS 26.5 SDK. [3][4]

## Why B is not yet a narrow, proven workaround

Snapzy's Release project sets `SWIFT_COMPILATION_MODE = wholemodule`, and the actual logged invocation uses `-O -whole-module-optimization`. Swift's official explanation says WMO allows optimizations across all module source files, including inlining, specialization, and reference-counting elimination. **Inference:** adding a target-level `-Onone` would not meet “only this file,” and a per-file setting cannot be assumed to override optimization inside this combined compilation. No source reviewed establishes a supported working one-file override for this exact Xcode invocation. [3][5][9]

Separately compiling a file/module, changing compilation mode, or applying function attributes would be distinct workaround designs needing validation; they are not demonstrated by B's description. In particular, an attribute on an uploader method would not automatically cover the compiler-generated destructor of the separate private helper identified in the crash. Avoid asserting either that B is impossible in every custom build system or that a simple Xcode setting makes it work. [3][4]

The best case for B is that ordinary cloud-disabled capture does not enter the affected upload workflow: `S3CloudProvider` routes files above **50 MiB** into the multipart uploader, and `ThreadSafeDictionary` is instantiated inside that upload method. Its queue has no self-starting periodic work in the inspected class. This supports a hypothesis of little **direct** idle/capture cost for a truly isolated change. It does not prove all executable code remains otherwise identical, that the crash is bypassed, or that restructured compilation preserves WMO's effects on capture latency. [4][7][9]

## Consequence of the recommendation

Use the existing provisional macOS-only direction for the v1 baseline work and label Snapzy **excluded because the inspected Release build crashes the compiler; no signed Release measurement available**. Do not relabel Debug, unsigned, or patched-build measurements as the missing comparator. Derive any macOS-relative targets from actual measurements rather than treating the placeholders as verified results. This research supplies the recommendation; it makes no changes to decisions, tickets, the clone, or the measurement implementation. [1–3]
